## 阶段一：技术方案与小程序原型

### 需求

设计点单小程序整体技术方案（原生框架、可运行、真机可预览调试、能快速上线并支持增长），
覆盖技术选型、目录与模块、页面与组件、数据与接口、登录与用户体系、性能与分包、上线审核、用户获取与留存。

### 方案与决策

| 决策 | 理由 |
| --- | --- |
| 微信原生框架（非 Taro/uni-app） | 单端投放、包体最小、平台新能力零适配 |
| 不引组件库，自建 stepper / sku-popup | 主题换肤需要完全掌控 CSS 变量 |
| 自研发布订阅 store（不引 MobX） | 只有一个购物车状态中心，引库属过度设计 |
| 金额全程「分」整数 | 杜绝浮点误差；明细行唯一键 `dishId#spicyId` |
| emoji + CSS 渐变占位图 | 零图片资源，真机样式永不塌陷 |
| 菜单数据放 `mock/menu.js` | 前后端菜单单一事实来源（后续演进为两份同步文件） |

### 产出

- 技术方案文档（13 章，已归档至 `docs/archive/`）
- 小程序工程（现为 `miniprogram/`）：点单/购物车/结算/订单/我的 5 页 + 2 组件

### 发现并修复

`buildTimeline` 中 `STATUS_META.step`（1-based）与 `TIMELINE_STEPS`（0-based）错位，
导致 `READY` 状态误标「订单完成」为已完成。

## 阶段四：交付级后端（单服务时代）

### 需求

交付级测试 + 商用可落地：保证不崩溃、性能最优、高并发、无 bug、交互合理、该有功能必须有；
接入微信登录与微信支付。

### 方案要点（可复用的架构决策）

| 决策 | 理由 |
| --- | --- |
| **零 Web 框架**（自研 http.js，仅 mysql2+ioredis） | 供应链面最小；过载保护/优雅关闭/错误码语义完全可控 |
| **服务端计价**：客户端 amount 一律丢弃 | 杜绝改价 |
| **防超卖**：`UPDATE ... WHERE stock >= ?` + affectedRows | 不存在「先查再减」竞态 |
| **结算代码唯一**：`settlePaid()` 微信回调与 Mock 共用 | 不会「mock 能过、真实环境挂」 |
| **订单号** `LBZ+yyyyMMdd+8位全局序列` | 秒级时间戳+随机数并发必撞 |
| **取号**：事务内 `SELECT ... FOR UPDATE` | 连接池下 `LAST_INSERT_ID` 要求同连接，会串号 |
| **Redis 可降级** | 挂了照常跑：缓存穿透 DB、限流/锁退化进程内 |
| **已支付不能直接取消** | 资金安全，必须走退款 |

### 产出

- 后端服务（18 表 / 42 接口 / 商家接单后台）
- 微信登录 code2session + 支付 v3（签名/验签/AES-GCM 解密/查单/退款）完整实现
- 测试 356 项断言全绿（含并发：库存 20/并发 60 精确卖出 20）

### 并发/真实后端才暴露的 11 个缺陷（节选）

1. P1 已支付订单能直接取消 → 钱不退
2. P1 优惠券核销 SQL 别名覆盖 → 券根本核销不了
3. P1 订单号并发必撞 / 取号串号
4. P2 登录限流按 IP 30/分钟 → 餐厅 NAT 全场被锁死（放宽到 300/分钟）
5. P2 超大 body `destroy()` 掐连接 → 客户端只见"网络异常"

## 阶段五：连锁版后端管理系统

### 需求（8 项）

① 直营+加盟权限模型与数据隔离 ② 保留并增强定位 ③ 可配置主题切换
④ 启动服务 + 代码 review + 可验收测试 ⑤ 架构/模块/接口/数据结构说明
⑥ 安全防攻击防逆向 ⑦ 美团团购券核销 ⑧ 优惠券模块

### 方案要点

| 子需求 | 方案 |
| --- | --- |
| ① | 5 角色 × 20 权限点；**隔离在 SQL 层**（`rbac.applyScope` 产出 `AND store_id IN (...)`）；加盟商独立角色（经营主体 vs 雇员） |
| ② | Haversine 排序；**无坐标也返回列表**（`needLocation` 引导）；拒绝授权不阻断 |
| ③ | 门店级 > 品牌级；**令牌差异式合并**（不整套替换）；预置模板一键套用；令牌注入三重防护 |
| ⑦ | Provider 可插拔（mock/meituan）；**三层防重**：本地查重 → 平台校验 → DB 唯一键；撤销不释放券码（防套现） |
| ⑧ | 三券型（现金/锅底/折扣）；三重限领全靠条件更新；**抵扣口径收口** `calcDiscount()` |
| ⑥ | scrypt+独立盐、锁定、首登改密、安全响应头、日志脱敏、全参数化 SQL |

### 产出

- 连锁 schema（27 表：品牌/门店/门店菜品覆盖/员工/授权/审计/主题/券/团购券）
- 管理后台单页（现为 `admin-web/`）
- `test/chain.test.js` 160 项连锁验收测试

### 审查发现并修复（重要）

1. **P1 越权**：`toggleTheme/deleteTheme` 缺门店范围校验 → 区域经理能关别家门店主题。
   根因：**权限点校验被当成了范围校验**。已复查全部管理接口。
2. P1 定向发券忽略 REST 路径参数
3. P2 默认门店按 id 字母序落在非总店 → 直营优先 + 编码升序
4. P2 全站无安全响应头 / 日志脱敏不全

## 阶段七：全需求复盘

### 做法

逐项核对历轮需求与产出。专门排查「有判断无动作、有提示无落库、有配置无使用」类隐蔽缺陷。

### 发现并修复 5 项

1. **P1 库存占用**：超时未支付订单**只报错不关单**——有 `PAY_TIMEOUT_MIN` 配置、有超时分支、
   有「订单已保存 15 分钟」提示，但不关单不回滚 → 库存被脏单永久占用，前端"明明有货却售罄"。
   修复：抽 `closeUnpaidOrder()` 供取消/超时/定时三条路径共用；prepay 先关单再报错；
   列表/详情惰性清理；60s 定时兜底（条件更新天然幂等，多实例无需选主）。
2. P3×4：setTimeout 未清理、URL 参数名 `token` 误导、领券误重试、文档断言数未同步。

### 关键经验

- **"提示了但没做"是最隐蔽的缺陷**：grep 配置项名看它被"读"还是被"用"；对应自动执行的动作搜 `setInterval/cron`。
- 回滚逻辑必须**单一收口成函数**：取消/超时/退款各写一份，迟早漏回滚库存。

## 阶段八：拆分为四个独立目录（本次）

### 需求

拆为小程序前端 / 小程序后端 / 管理系统前端 / 管理系统后端四个独立目录，
各自含源码、配置、依赖清单与说明；清理跨目录混用与冗余；根目录说明职责关系。

### 核心架构决策

**领域规则不复制**。状态机/防超发/防重核销/库存回滚只有一份（在 miniprogram-server），
admin-server 通过 `internalApi` 调 `/internal/*`（`X-Internal-Token` 鉴权）。
若复制两份，必出「小程序端改了、管理端没改」的分裂。

```
admin-server ──internal──▶ miniprogram-server
  订单推进/拒单/退款审核        （状态机一份）
  团购券核销/撤销              （防重一份）
  定向发券                    （防超发一份）
  门店库存与上下架             （回滚与缓存失效一份）
  订单列表/详情 DTO            （展示口径一份）
admin-server 直连 DB：门店/员工/菜品/主题/券模板/审计（纯 CRUD，无状态机）
```

### 执行步骤与涉及文件

| 步骤 | 文件 |

| 抽出流转规则 | `miniprogram-server/src/routes/flow.js`（从管理路由剥离） |

| 前端工程化拆分 | `admin-web/{index.html,styles.css,app.js}`（从内联抽出） |
| 种子数据解耦 | `miniprogram-server/data/menuSeed.js`（后端不再读前端源码） |
