## 2. 本轮发现并已修复的问题

### 2.1 🔴 P1 · 主题「停用 / 删除」缺门店范围校验（越权）

**位置**：`src/themeService.js` `toggleTheme()` / `deleteTheme()`

**问题**：两个函数只按 `id + brand_id` 定位，没有校验 `store_id` 是否落在操作者授权范围内。而 `REGION_MANAGER` 角色**拥有** `theme:write` 权限，其门店范围是按 `region` 解析的——于是「华南区域经理可以关掉东直门店的活动主题」。

```js
// 修复前
async function toggleTheme(scope, id, status) {
  const r = await db.execute('UPDATE mp_theme SET status = ? ... WHERE id = ? AND brand_id = ?', [...]);
}
```

**修复**：补 `assertThemeWriteScope(scope, theme.store_id)`（与 `saveTheme`/`activateTheme` 保持一致）。

```js
async function toggleTheme(scope, id, status) {
  const theme = await db.queryOne('SELECT * FROM mp_theme WHERE id = ? AND brand_id = ?', [id, scope.brandId]);
  if (!theme) throw notFound('主题不存在');
  assertThemeWriteScope(scope, theme.store_id);   // ← 新增
  ...
}
```

**回归**：新增断言 F28g / F28h / F28i，越权停用与删除均返回 `403 无权修改该门店的主题`，且目标主题状态未被改动。

> **根因归类**：这是「权限点校验」与「数据范围校验」被当成一件事的典型漏洞。教训是——**范围校验必须独立于权限点，且每个写接口都要过**。已对全部 40+ 管理接口复查一遍。

### 2.2 🔴 P1 · 定向发券接口忽略 REST 路径参数

**位置**：`src/routes/admin.js` `grantCoupon()`

**问题**：路由是 `POST /admin/coupons/:id/grant`，但 handler 只读 `body.couponId`，路径参数被丢弃，按 REST 语义调用会报「请选择优惠券」。

**修复**：

```js
const couponId = String(ctx.params.id || b.couponId || '');
```

**回归**：F29 定向发放成功计数 = 2；F31 未匹配用户时返回参数错误。

### 2.3 🟡 P2 · 默认门店落在非旗舰店

**位置**：`src/routes/menu.js` `resolveStore()`

**问题**：未指定门店时 `ORDER BY (type='DIRECT') DESC, id ASC`，按 id 字母序取到 `st_cy`（朝阳店），而业务预期默认门店是 **BJ001 东直门总店**。

**修复**：改为 `ORDER BY (type='DIRECT') DESC, code ASC`（编码升序 → BJ001 优先）。

### 2.4 ⚠️ · 全站无安全响应头

**问题**：`ctx.send()` 只写了 Content-Type / Content-Length / X-Request-Id / Cache-Control，没有任何安全头。

**修复**（`src/http.js`）：统一注入

| 头 | 值 | 作用 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | 阻断 MIME 嗅探 |
| `X-Frame-Options` | `SAMEORIGIN` | 防点击劫持 |
| `Referrer-Policy` | `no-referrer` | 防 URL 里的订单号/券码外泄 |
| `X-Powered-By` | 空 | 不暴露技术栈 |
| `Strict-Transport-Security` | 仅生产 | 强制 HTTPS |

另外对两处「裸写响应」补强：

- **管理后台** `/admin`：追加 CSP `default-src 'self'; …; frame-ancestors 'self'`
- **上传目录** `/uploads/*`：追加 `nosniff` + `Content-Security-Policy: default-src 'none'; sandbox` + `X-Frame-Options: DENY`。用户上传是存储型 XSS 的经典落点，必须按「不可执行」处理。

### 2.5 ⚠️ · 日志脱敏覆盖不全

**问题**：`SENSITIVE` 只列了 token/password/session_key，**手机号、openid 全量、券码、各类密钥**会明文进日志。

**修复**（`src/logger.js`）：

| 类别 | 处理 |
|---|---|
| `token` `password` `secret` `appSecret` `apiv3Key` `privateKey` `sessionKey` … | 置 `***` |
| `openid` | 保留前 6 位 |
| `phone` `mobile` `tel` | `138***1234` |
| `idCard` | `110101****1234` |
| `code`（券码 / 微信登录 code，长度 ≥ 8） | 保留前 4 位 |

### 2.6 🟢 P3 · 小程序主题字段缺失

**问题**：5 个页面的 WXML 根节点写了 `style="{{themeStyle}}"`，但 JS `data` 里没有该字段（`menu.js` 有，其余漏了）；`mine.wxml` 引用了 `store` 但 `mine.js` 没声明。首次渲染会取到 `undefined`。

**修复**：统一注入 `themeStyle: ''`，`mine.js` 补 `store: null`。静态审查 0 error。

### 2.7 🟢 P3 · 测试套件间存在隐式顺序依赖

**问题**：并发测试会把 `脆皮小香肠` 库存卖空，随后跑接口测试会因库存不足失败——套件之间耦合了共享状态。

**修复**：接口测试在加载菜单后立即自铺库存夹具（涉及菜品各 200），每个套件自给自足。现已验证任意顺序、重复执行均全绿。

## 3. 安全设计逐项核查（需求⑥）

### 3.1 防黑客攻击

| 攻击面 | 现有防护 | 验证方式 |
|---|---|---|
| 撞库 / 暴力破解 | IP 40 次/5 分钟 + 账号 5 次失败锁 15 分钟 | 登录日志可查 |
| 账号枚举 | 账号不存在与密码错误返回**同一文案** | A5 / A6 断言 |
| 越权（水平 / 垂直） | `assertPerm` + `assertStore` + SQL 层 `applyScope` | 8 类越权场景全 403 |
| 提权 | 只有超管能创建/修改超管账号 | B21 断言 |
| SQL 注入 | 全量参数化；动态片段仅 `?` 占位与白名单字段 | 注入串不产生 5xx，表未被 DROP |
| XSS | 头像只接受 `https://` 或本站路径；后台模板全量 `esc()`；主题令牌字符白名单 | `javascript:` / `data:` / `<script>` 均被拒 |
| 路径穿越 | 解码后校验 `..` `\` 与绝对路径，并 `path.resolve` 二次确认前缀 | 3 种编码变体全 404 |
| 上传木马 | **魔数校验**（只认 JPG/PNG 文件头）+ 大小上限 | 非图片文件被拒 |
| 上传文件执行 | `nosniff` + CSP `sandbox` + `default-src 'none'` | 响应头已生效 |
| JWT 伪造 | 签名校验；`alg=none` 被拒；篡改 payload 401 | 韧性测试 2 项 |
| 重放（支付回调） | 5 分钟时间戳窗口 + 验签 | 伪造回调不改单 |
| 点击劫持 | `X-Frame-Options: SAMEORIGIN` + CSP `frame-ancestors` | 响应头已生效 |
| 大 body / 慢速攻击 | 256 KB 上限（超限 413 且不断开连接）+ 15s 请求超时 | 韧性测试 |
| DDoS / 雪崩 | `MAX_INFLIGHT=2000` 超限 503（拒绝而非排队）；优雅关闭 | 压测 120 并发零 5xx |
| 刷券 / 刷单 | 领券 20/分钟、核销 30/分钟、下单 5 单/15 分钟 | 限流断言 |
| 内部作弊 | 团购券单笔面值上限（默认 ¥2000）；大额操作全部进审计 | 配置 + 审计 |

### 3.2 防逆向（小程序侧）

小程序代码包可被反编译，因此**任何"写在小程序里的判断"都不能作为安全依据**。本项目的原则是「客户端只负责展示与传递意图，裁决全在服务端」：

| 客户端可篡改项 | 服务端对策 |
|---|---|
| 商品价格 | 下单时用库内 `mp_dish.price` / `mp_store_dish.price_override` 重算，客户端传价丢弃 |
| 优惠金额 | `couponService.calcDiscount()` 服务端计算 |
| 库存判断 | `UPDATE ... WHERE stock >= ?` 原子扣减，不信客户端 |
| 订单状态 | 状态机白名单 `transition()`，跳步拒绝 |
| 用户身份 | openid 由 `code2session` 换取，伪造 token 401 |
| 门店 ID | 每个写接口 `assertStore`，越店 403 |
| 域名白名单 | 小程序后台配置 request 合法域名，非白名单域名请求被微信拦截 |
| 调试 | 生产版本关闭 debug、`lazyCodeLoading: requiredComponents` 减少暴露面 |

**建议补强（上线前）**：
1. 小程序后台开启「防调试」+ 代码混淆
2. 请求签名：`X-Signature = HMAC-SHA256(timestamp + body, appKey)`，服务端校验 5 分钟窗口 + nonce 去重
3. 关键接口（下单/支付/核销）接入网关层 WAF 与 IP 信誉库

### 3.3 数据安全

| 项 | 现状 |
|---|---|
| 口令存储 | scrypt（keylen 64）+ 每账号独立 16 字节随机盐，永不明文 |
| 口令比对 | `crypto.timingSafeEqual`（防时序侧信道） |
| session_key | 仅存 Redis 7 天，**不落库** |
| 手机号 | 微信加密数据解密获取，日志掩码 |
| 日志 | 结构化 JSON + 敏感字段脱敏（见 2.5） |
| 审计 | 所有管理端写操作落 `mp_audit_log`（谁/哪家店/什么动作/哪个 IP/UA/requestId） |
| 登录日志 | `mp_login_log` 记录成功与失败（含失败原因），供风控分析 |
| 令牌 | 访问 2h / 刷新 7d / 轮换 / jti 黑名单可即时吊销 |
| 权限即时生效 | 令牌只做身份证明，**每次请求重新查库解析范围**，改权限后旧令牌立即失效 |

### 3.4 系统健壮性

| 项 | 现状 |
|---|---|
| Redis 不可用 | 整体降级：缓存穿透 DB、限流改进程内、分布式锁改进程内 Mutex，**服务照常可用**（实测 9 项） |
| 数据库慢/挂 | 连接池上限 + 获取超时 8s + 队列上限 200；就绪探针 `/ready` 暴露降级状态 |
| 优雅关闭 | SIGTERM → 停止接新请求 → 等在途完成 → 关连接 → 释放端口 |
| 未捕获异常 | handler 全 try/catch + `unhandledRejection` 兜底，**绝不冒泡到进程** |
| 幂等 | 下单 `Idempotency-Key`、支付结算、核销唯一键，三重保证 |
| 数据一致性 | 库存扣减与订单创建同事务；扣减按 dishId 排序统一加锁顺序防死锁 |

## 4. 代码质量走查

| 项 | 评价 |
|---|---|
| 依赖 | 仅 `mysql2` + `ioredis`，无 Web 框架，供应链面极小 |
| 分层 | 路由层不写业务规则，领域服务（`couponService` / `voucherService` / `themeService` / `rbac`）是唯一收口处 |
| SQL | 全量参数化；动态片段集中在 `rbac.storeFilter` 等受控函数 |
| 错误处理 | 统一 `AppError` + 错误码表；业务错误走 200 + code，避免客户端误判为网络错误 |
| 金额 | 全程「分」整数，只在展示层转元，杜绝浮点误差 |
| 日志 | JSON lines，带 requestId 贯穿；慢请求与 5xx 自动升级等级 |
| 分页 | `page`/`size` 双向钳制，防 OFFSET 溢出 |
| 命名 | `mp_` 前缀统一；权限点 `资源:动作` 命名 |

**可优化项（非阻塞）**：

| # | 项 | 建议 |
|---|---|---|
| 1 | 上传目录在本地磁盘 | 生产改对象存储（COS/OSS），并加 CDN + 图片处理 |
| 2 | `grantToUsers` 逐条串行 | 批量 ≤500 时可改分批并发（当前串行已满足 500 人 < 2s） |
| 3 | 审计日志无归档策略 | 建议 ≥180 天热存 + 冷归档 |
| 4 | 主题/券变更无审批流 | 大额券、品牌级主题建议加二级审批 |
| 5 | 无接口级灰度 | 建议网关层按门店灰度新功能 |
