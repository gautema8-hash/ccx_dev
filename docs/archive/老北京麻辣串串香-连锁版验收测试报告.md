## 2. 怎么复现

### 2.1 起服务

```bash
cd server
npm install                  # 只装 mysql2 + ioredis
node src/db.js migrate       # 建 27 张表（幂等）
node src/db.js seed          # 种子：1 品牌 / 5 门店 / 30 菜品×5 门店 / 6 员工 / 4 主题 / 5 券模板
node src/index.js            # 监听 3000
```

确认就绪：

```bash
curl http://127.0.0.1:3000/ready
# {"code":0,"data":{"db":true,"redis":true,"degraded":false}}
```

```bash
npm test                      # 全部 334 项（api → chain → concurrency → resilience）
```

**隔离实现要点**（不是「查出来再过滤」）：

```sql
-- 无授权门店时返回空结果，而不是报错或返回全量
AND store_id IN (...)   -- 或  AND 1=0
```

最坏情况是「查不到数据」，不是「数据泄露」。

## 5. 测试设计原则（为什么这些断言能代表"可交付"）

1. **断言的是「最坏情况」而不是「正常路径」**：越权时兜底方向必须是「查不到」而不是「泄露」；库存并发时必须是「不多卖一份」而不是「大致够」。
2. **每个套件自给自足**：接口测试自己铺库存夹具，避免套件间隐式顺序依赖（本轮已修复）。
3. **幂等可重复运行**：连锁测试会复位会员日主题、复用/复位测试账号，连续执行 3 次结果一致。
4. **失败信息带上下文**：断言失败时打印服务端 `code` 与 `message`，不做"黑盒猜谜"。
5. **限流不靠削弱安全策略来绕过**：管理端登录有 IP 限流（40/5min），测试用令牌缓存规避，而不是调高阈值——生产策略保持原样。

### 已知的环境约束

| 约束 | 说明 |
|---|---|
| 管理端登录 IP 限流 | 40 次 / 5 分钟。连续多轮跑全套可能触发，测试已用令牌缓存规避；手工重跑若遇 `42900`，等 5 分钟或清 `lbz:r:stafflogin:ip:*` |
| 库存为共享状态 | 各套件已自铺夹具，但并发测试会卖空它操作的菜品，属预期 |
| 美团真实接口 | 默认 `VOUCHER_PROVIDER=mock`，E 组验证的是核销链路与防重逻辑；接入真实凭据后 `provider.verify()` 的行为需按美团文档再验一遍 |
