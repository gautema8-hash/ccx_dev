### 1.2 为什么坚持「零 Web 框架」

| 考量 | 结论 |
|---|---|
| 供应链安全 | 依赖越少，被投毒的面越小（需求⑥）。全链路仅 2 个直接依赖，可人工审计 |
| 性能 | 自研 `http.js` 不做反射/装饰器/中间件洋葱，**实测混合负载 P50=50ms、P95=168ms、零 5xx** |
| 可控性 | 过载保护、优雅关闭、请求体上限、错误码语义全部自己说了算，不被框架默认行为坑 |
| 交付 | `npm i` 只需 2 个包，冷启动 < 1s，运维无门槛 |

### 1.3 连锁数据模型（核心抽象）

```
品牌 Brand ──┬── 门店 Store（type: DIRECT 直营 / FRANCHISE 加盟）
             │        ├── 门店菜品覆盖 StoreDish（本店库存 / 本店停售 / 门店改价）
             │        ├── 门店级主题 Theme（覆盖品牌级）
             │        └── 订单 Order（冗余 brand_id / store_id / store_type）
             ├── 菜品 Dish（总部：卖什么、指导价、是否上架）
             ├── 优惠券模板 Coupon（可限定 store_ids）
             ├── 主题 Theme（品牌级）
             └── 员工 Staff ── 员工门店授权 StaffStore
```

**一句话概括分工**：总部决定「卖什么、卖多少钱」，门店决定「有多少货、今天卖不卖、要不要改价」。

## 3. 权限模型与数据隔离（需求①）

### 3.1 角色与权限点

权限点共 20 个，按「资源:动作」命名：

| 域 | 权限点 |
|---|---|
| 品牌 | `brand:write` |
| 门店 | `store:read` `store:write` |
| 员工 | `staff:read` `staff:write` |
| 菜品 | `dish:read` `dish:write` `dish:stock` |
| 订单 | `order:read` `order:advance` `order:cancel` |
| 优惠券 | `coupon:read` `coupon:write` `coupon:issue` |
| 主题 | `theme:read` `theme:write` |
| 团购券 | `voucher:verify` `voucher:read` `voucher:refund` |
| 经营 | `stats:read` `audit:read` |

| 角色 | 数据范围 | 权限点 |
|---|---|---|
| **BRAND_ADMIN** 品牌超管 | 全部门店（`all_stores=1`） | `*`（全部） |
| **REGION_MANAGER** 区域经理 | 按 `region` 解析门店 | 全部只读 + `dish:stock` `order:advance` `order:cancel` `coupon:write` `coupon:issue` `theme:write` `voucher:verify` `audit:read` |
| **STORE_MANAGER** 店长 | 被授权的门店 | 全部只读 + `dish:stock` `order:advance` `order:cancel` `voucher:verify` |
| **STAFF** 店员 | 被授权的门店 | `store:read` `dish:read` `order:read` `order:advance` `voucher:verify` |
| **FRANCHISE_OWNER** 加盟商 | 仅自己的加盟店 | 同店长 |

**加盟商用独立角色而不是「店长 + 限定门店」**，因为两者的合规诉求不同：加盟商是独立经营主体，需要「只看自己、可看经营统计」，而店长是雇员，不应看到门店毛利类数据。

### 3.2 数据隔离的三条铁律

```
① 每个管理接口：requireStaff（身份） → assertPerm（能不能做） → assertStore/scope（能在哪家店做）
② 所有列表查询必须走 rbac.applyScope()，禁止业务代码自己拼 store_id 条件
③ 所有写操作必须 staffAuth.audit() 留痕
```

**为什么必须在 SQL 层隔离**（不是「查出来再过滤」）：

```js
// rbac.js —— 统一产出 SQL 片段
function storeFilter(ctx, column) {
  const scope = ctx.scope;
  if (!scope) return { sql: ' AND 1=0 ', params: [], empty: true };   // 没登录 → 什么都查不到
  if (scope.allStores) return { sql: '', params: [], empty: false };  // 超管 → 不加条件
  const ids = scope.storeIds || [];
  if (!ids.length) return { sql: ' AND 1=0 ', params: [], empty: true }; // 无授权门店 → 查不到
  return { sql: ` AND ${column} IN (${ids.map(() => '?').join(',')}) `, params: ids, empty: false };
}
```

对照两种实现的最坏情况：

| 实现 | 漏判一处时的后果 |
|---|---|
| 查出来再过滤 | **数据泄露**（加盟商 A 看到加盟商 B 的营业额） |
| SQL 层隔离 | **查不到数据**（功能不可用，但不泄露） |

安全兜底方向必须是后者。

### 3.3 越权防护的实测结论

| 场景 | 结果 |
|---|---|
| 店长查别家门店菜品 `GET /admin/dishes?storeId=st_cy` | `403 无权操作该门店` |
| 加盟商查别家门店订单 `GET /admin/orders?storeId=st_hd` | `403 无权操作该门店` |
| 店长改别家门店主题 | `403` |
| 区域经理改品牌信息（无 `brand:write`） | `403` |
| **区域经理创建品牌超管账号（提权）** | `403 只有品牌超管可以创建/修改品牌超管账号` |
| **有 `coupon:write` 但门店越权发券** | `403 不能把券限定给自己无权管理的门店：st_dz` |
| 店员改库存（无 `dish:stock`） | `403` |
| 无授权门店的区域经理查门店 | 返回空列表（不是报错，也不是全量） |

## 4. 主题系统（需求③）

### 4.1 解析优先级

```
门店级主题（store_id 非空）  >  品牌级主题（store_id 为空）
    ↓ 同一层级内
在生效时间窗内 + status=1 的，取 priority 最大者
    ↓ 都没命中
默认主题 Normal（小程序永远拿得到一份可用令牌）
```

```sql
SELECT * FROM mp_theme
WHERE brand_id = ? AND status = 1
  AND (store_id = ? OR store_id = '')
  AND (start_at = 0 OR start_at <= ?)
  AND (end_at = 0 OR end_at >= ?)
ORDER BY (store_id = ?) DESC, priority DESC, updated_at DESC
LIMIT 1
```

`ORDER BY (store_id = ?) DESC` 是门店级优先的关键：命中门店级的行该值为 1，排在前面。

### 4.2 令牌设计：差异式覆盖，不是整套替换

| 做法 | 问题 |
|---|---|
| 整套替换 | 新增主题要把 15 个令牌全抄一遍；改默认色要改 N 处 |
| **差异式（本项目）** | 只存差异，解析时 merge 到默认令牌上 |

默认令牌 15 个：`primary` `primaryDark` `primaryWeak` `accent` `text` `sub` `line` `bg` `card` `navBg` `navText` `bannerText` `bannerSub` `barBg` `badge`（与小程序 `app.wxss` 的 CSS 变量一一对应）。

### 4.3 预置模板（运营一键套用，不用自己调色）

| Key | 名称 | 配色 | 用于 |
|---|---|---|---|
| `NORMAL` | 标准主题 | 品牌红金 `#C62828` + `#FF8F1F` | 日常营业 |
| `CAMPAIGN` | 品牌活动日 | 玫红 `#D81B60` + 琥珀 `#FFB300` | 周年庆 / 开业季 |
| `HOLIDAY` | 国庆节假日 | 正红 `#C62828` + 金黄 `#FFC107` | 节庆 |
| `MEMBER_DAY` | 会员日 | 黑金 `#2E2A26` + `#C9A227` | 每周会员日 |

### 4.4 一键切换的语义

`activateTheme` 在一个事务里做两件事：

1. 目标主题：`status=1, priority=1000, start_at=0, end_at=0`（立即生效、无时间窗限制）
2. 同层级其它主题：`priority=0`（**降权不删除**，方便随后切回来）

### 4.5 令牌注入防护

主题令牌最终会以 `style="--c-primary:xxx"` 注入小程序页面，属于「服务端内容 → 前端渲染」的注入面，做了三重收敛：

```js
Object.keys(override).forEach((k) => {
  if (Object.prototype.hasOwnProperty.call(DEFAULT_TOKENS, k)) {              // ① 白名单键
    const v = String(override[k] == null ? '' : override[k]).slice(0, 120);   // ② 长度截断
    if (/^[#(),.%\-\s\w\u4e00-\u9fa5]*$/.test(v)) out[k] = v;                 // ③ 字符白名单
  }
});
```

实测：`primary: 'url(javascript:alert(1))'` → 回落默认 `#C62828`；`evilKey` → 丢弃；`bannerText: '<script>…'` → 置空。

### 4.6 小程序端落地

```js
// services/chain.js
applyTheme(page) {
  const app = getApp();
  const style = app.globalData.themeStyle || tokensToStyle(DEFAULT_TOKENS);
  page.setData({ themeStyle: style, themeTokens: tokens, themeName: app.globalData.theme.name });
  // 导航栏配色同步（导航栏不在 WXML 树内，必须走 API 设置）
  wx.setNavigationBarColor({ frontColor: '#ffffff', backgroundColor: tokens.navBg });
}
```

页面根节点 `<view class="page" style="{{themeStyle}}">`，CSS 变量向下继承，全页变色零 JS 参与。切门店时重新拉主题 → 清空菜单缓存 → 刷新页面，三步在 `pages/store-list` 的 `commit()` 里串行完成。

## 5. 安全设计（需求⑥）

### 5.1 管理端账号

| 措施 | 实现 |
|---|---|
| 口令散列 | `scrypt`（keylen 64）+ **每账号独立 16 字节随机盐**，不用 MD5/SHA1 |
| 口令比对 | `crypto.timingSafeEqual`，杜绝时序侧信道 |
| 失败锁定 | 连续 5 次失败锁定 15 分钟（DB 计数 + Redis 双层） |
| 撞库防护 | IP 级限流 40 次 / 5 分钟 |
| 账号枚举防护 | 账号不存在与密码错误返回**完全相同的文案**「账号或密码错误」 |
| 弱口令拦截 | ≥8 位且同时含字母与数字，且禁止 `123456/password/admin` 开头 |
| 首登强制改密 | `must_change_pwd=1` 时只放行改密/登出/个人信息三个接口 |
| 令牌时效 | 访问令牌 2h，刷新令牌 7d |
| 令牌吊销 | jti 黑名单，登出即时生效 |
| **权限即时生效** | 令牌只做身份证明，**每次请求重新查库解析门店范围**——改权限后旧令牌立即失效，不留越权窗口 |

### 5.2 接口层

| 威胁 | 防护 | 实测 |
|---|---|---|
| 越权访问 | `assertPerm` + `assertStore` 双断言 | 8 个越权场景全部 403 |
| 提权 | 只有超管能创建/修改超管账号 | 区域经理建超管 → 403 |
| SQL 注入 | 全量参数化查询，无字符串拼接 | 注入串不产生 5xx，表未被 DROP |
| XSS | 头像只接受 `https://`/本站路径；主题令牌字符白名单 | `javascript:` / `data:` 被拒 |
| 路径穿越 | `/uploads/../package.json` 等 3 种编码变体 | 全部 404 |
| JWT 伪造 | `alg=none` 攻击、篡改 payload | 401 |
| 大 body 攻击 | 256 KB 上限 | 413（且连接不被粗暴断开） |
| 分页溢出 | `page` ≤ 10000、`size` 双向钳制 | `page=1e308` 安全 |
| 重放攻击（支付） | 5 分钟时间戳窗口 | 回调验签后才改单 |
| 爬虫/刷券 | 领券 20/分钟、核销 30/分钟（按用户/员工维度） | — |
| 过载 | `MAX_INFLIGHT=2000`，超限 503 | 压测 120 并发零 5xx |

### 5.3 小程序端防逆向（需求⑥）

小程序代码包天然可被反编译，因此**任何"写在小程序里的判断"都不能作为安全依据**，全部下沉到服务端：

| 客户端能看到/改的 | 服务端的对策 |
|---|---|
| 商品价格 | 下单时用 `mp_dish` / `mp_store_dish` 的库内价重算，**客户端传的价格一律丢弃** |
| 优惠金额 | `couponService.calcDiscount()` 服务端计算 |
| 库存数字 | 扣减用 `UPDATE ... WHERE stock >= ?` 原子语句，不信客户端判断 |
| 订单状态 | 状态机白名单 `transition()`，跳步直接拒绝 |
| 用户身份 | openid 由 `code2session` 换得，客户端伪造的 token 一律 401 |
| 门店 ID | 每个写接口 `assertStore`，越店即 403 |
| 接口签名/密钥 | 生产启用 `HTTPS + 微信网关`；JWT 短时效 |

上线加固清单（详见《代码审查与安全加固报告》）：小程序后台开启「防调试」、请求签名（`X-Signature = HMAC(timestamp+body)`，5 分钟窗口）、接口网关限流、敏感字段日志脱敏（已实现）。

## 6. 关键实现细节

### 6.1 单号生成（连接池下的坑）

```js
// ❌ 错误做法：LAST_INSERT_ID 依赖「同一条连接」，连接池下会串号
// ✅ 正确做法：事务内行锁
async function nextSeq(key) {
  return db.tx(async (tx) => {
    await tx.execute('INSERT INTO mp_seq (k, v) VALUES (?, 1) ON DUPLICATE KEY UPDATE v = v + 1', [key]);
    const row = await tx.queryOne('SELECT v FROM mp_seq WHERE k = ? FOR UPDATE', [key]);
    return Number(row.v);
  });
}
```

订单号 = `LBZ` + `yyyyMMdd` + 8 位全局序号（旧的「秒级时间戳 + 3 位随机」在并发下会碰撞）。
取餐号按 `pickup:{storeId}:{date}` 独立循环——**连锁多店共用一个号池会串号**。

### 6.2 防超卖（原子扣减）

```sql
UPDATE mp_store_dish SET stock = stock - ?, sold = sold + ?, updated_at = ?
WHERE store_id = ? AND dish_id = ? AND status = 1 AND stock >= ?
```

`affectedRows === 0` 即库存不足。**不存在「先查后写」的竞态窗口**。
多菜品扣减按 `dishId` 排序统一加锁顺序，避免死锁。

实测：库存 20 / 并发 60 → 成功 20、拒绝 40、库存精确归零、`sold` 准确累加。

### 6.3 团购券核销（需求⑦）

**Provider 可插拔**：`VOUCHER_PROVIDER=mock` 本地规则（无凭据也能全链路跑通）/ `meituan` 真实开放平台。上线只改 `.env`，业务代码零改动。

**核销顺序（三层防重）**：

```
① 本地查重 mp_voucher（platform, code）
      ↓ 未核销
② 问平台 provider.verify()
      ↓ 有效
③ 面值上限保护（> ¥2000 需二次确认，防内部作弊）
      ↓
④ INSERT —— uk(platform, code) 唯一键是并发下的最后一道保险
```

```js
catch (e) {
  if (e && e.errno === 1062) throw bizError(CODES.STATE_CONFLICT, '该券已被核销，请勿重复操作');
  throw e;
}
```

**实测**：并发 10 次核销同一券码 → **只成功 1 次**，其余 9 次被唯一键挡下。

**其它要点**：
- 券码规范化 `normalizeCode()`：去空格/连字符 + 转大写，`mt88-2007 3546` ≡ `MT8820073546`
- 已核销时把「什么时候、在哪家店」原样告诉店员，便于追责
- 撤销核销只改 `status='REFUNDED'`，**券码不释放**——防止「撤销后再核销一次」套现
- 用户自助核销（SELF）与店员代客核销（STAFF）共用 `voucherService`，不留「自助通道没防重」的缺口
- 核销需门店在营业时间内（跨天营业时间由 `geo.isOpenNow` 正确判定）

### 6.4 优惠券（需求⑧）

**券型**：`CASH` 现金券 / `SOUP` 锅底券 / `DISCOUNT` 折扣券（88 = 8.8 折）

**抵扣口径统一收口**在 `calcDiscount(coupon, order)`，下单与「我的券可用性」共用，杜绝「列表显示可用、下单说不可用」：

```js
const base = coupon.type === 'SOUP' ? soupFee : goods + soupFee;
if (type === 'CASH')     discount = Math.min(value, base);
if (type === 'SOUP')     discount = Math.min(value, soupFee);
if (type === 'DISCOUNT') discount = Math.round(base * (100 - rate) / 100);
discount = Math.min(discount, gross);   // 抵扣不超过订单金额，不出现负数实付
```

**三重限领**（全部用「条件更新 + 计数」，不靠先查后写）：

| 约束 | 实现 |
|---|---|
| 总量 | `UPDATE mp_coupon SET issued = issued + 1 WHERE id = ? AND issued < total`，`affectedRows=0` 即已领完 |
| 每人限领 | `COUNT(mp_user_coupon) < per_user` |
| 每日限领 | `COUNT(mp_coupon_receive WHERE created_at >= 今日零点) < day_limit` |

**发放来源可追溯**：`NEW_USER`（注册自动）/ `CAMPAIGN`（活动）/ `MANUAL`（定向）/ `RECEIVE`（领券中心）。管理端定向发放支持按用户 id / 手机号 / openid 三种方式匹配，单批上限 500 人，失败逐条返回不中断批量。

**门店适用范围**：`store_ids` 为空 = 全品牌通用；非空则领券中心只在该门店展示、下单只在该门店可用。加盟商/区域经理**不能把券限定到自己无权管理的门店**（权限点校验之外的独立范围校验）。

实测抵扣：`满50减10` 抵扣 ¥10；锅底券只对锅底 ¥18 抵扣；8.8 折券按 `(20000+1800)×12% = ¥26.16`。

### 6.5 定位与附近门店（需求②）

```js
// geo.js —— Haversine，零依赖
function distanceKm(lat1, lng1, lat2, lng2) {
  const R = 6371, toRad = (d) => (d * Math.PI) / 180;
  const dLat = toRad(lat2 - lat1), dLng = toRad(lng2 - lng1);
  const a = Math.sin(dLat/2)**2 + Math.cos(toRad(lat1)) * Math.cos(toRad(lat2)) * Math.sin(dLng/2)**2;
  return 2 * R * Math.asin(Math.sqrt(a));
}
```

**保留并增强原有定位能力**：

| 原能力 | 现在 |
|---|---|
| 授权后拿坐标 | 保留；`wx.getLocation`（`requiredPrivateInfos` 已声明，用途说明写明「为你推荐附近门店」） |
| — | **新增**：未授权时不阻断，返回门店列表 + `needLocation=true`，前端提示「开启定位看最近门店」 |
| — | **新增**：拒绝授权后给「去设置」入口（`wx.openSetting`），状态条展示 DENIED/LOADING/IDLE |
| — | **新增**：按 Haversine 排序（营业中优先、其次距离）、50 km 半径、最多 20 家 |
| — | **新增**：`wx.openLocation` 一键导航（保留原有导航能力） |

**降级策略**：坐标非法（`lat=999`）不报错、不返回距离字段，只是不排序而已。

### 6.6 缓存与降级

| 场景 | 策略 |
|---|---|
| 菜单 | 按门店缓存（`menu:{storeId}`，60s）；带坐标请求不缓存（距离随位置变） |
| 改价/改库存/上下架 | 主动 `refreshMenuCache(storeId)` 失效 |
| Redis 不可用 | **整体降级**：缓存穿透到 DB、限流降级为进程内计数、分布式锁降级为进程内 Mutex —— 服务照常可用（实测 9 项降级场景全绿） |
| 优雅关闭 | 停止接新请求 → 等在途请求完成 → 关闭连接 → 释放端口 |
