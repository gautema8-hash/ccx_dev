## 1. 方案总览与关键结论

### 1.1 业务目标

| 维度 | 目标 | 本方案的支撑点 |
| --- | --- | --- |
| 快速上线 | 3 周内可提审，第 4 周全量 | 原生框架零构建、Mock-first 前后端并行开发 |
| 首批用户增长 | 首月 5,000 下单用户 | 桌贴码带参数进店 + 分享裂变券 + 微信搜一搜 + 订阅消息召回 |
| 点单效率 | 从扫码到下单 ≤ 90 秒 | 左分类右菜品双向联动、无规格菜品一键加购、辣度弹层默认值、锅底预选 |
| 稳定性 | 无崩溃、无白屏 | 全链路降级（菜单缓存、支付取消重回订单）、`wx.onError` 兜底 |

### 1.2 技术结论速览

| 决策项 | 结论 | 一句话理由 |
| --- | --- | --- |
| 开发框架 | **微信小程序原生框架**（WXML/WXSS/JS） | 单端投放 + 包体最小 + 平台新能力零适配成本 |
| 是否用 Taro / uni-app | 不用 | 无多端诉求，引入构建链只会拖慢上线与排障 |
| UI 组件库 | **不引 TDesign**，自建 2 个业务组件 | 点单页交互定制度高，省掉 npm 构建与 1 次审核风险 |
| 状态管理 | **自研轻量 store**（发布订阅 + Storage 持久化） | 免 MobX/Redux 体积与构建步骤，购物车逻辑仅 ~200 行 |
| 渲染引擎 | WebView 渲染（默认） | 分类联动依赖 `createSelectorQuery` 批量量高，WebView 更稳；Skyline 留作 V2 评估 |
| 菜品图像 | **emoji + CSS 渐变占位** | 零图片资源 = 零 CDN/零加载失败/真机样式永不塌陷 |
| 金额单位 | **分（整数）** | 杜绝浮点误差，全链路统一 |
| 规格建模 | 辣度记在**明细行**（`dishId#spicyId`） | 串串香「同串不同辣」是核心诉求，而非整单统一 |
| 分包策略 | 主包 6 页 + `packageUser` 分包 | 主包体积预算 ≤ 1.5MB，成长型页面全部下沉 |
| 联调方式 | **Mock 优先**，`services` 层一键切真实后端 | 前后端并行，前端不被接口进度阻塞 |

### 1.3 主要风险与预案

| 风险 | 影响 | 预案 |
| --- | --- | --- |
| 类目/资质不过审 | 无法上线 | 提前 2 周办餐饮类目 + ICP 备案，准备《食品经营许可证》 |
| 支付未接入商户号 | 无法收款 | 用「模拟支付」开关 `MOCK_PAY` 先跑通流程，商户号并行申请 |
| 用餐高峰期接口抖动 | 点单卡死 | 菜单 60s 内存缓存 + Storage 兜底 + 下单失败保留购物车 |
| 分类联动抖动 | 体验差 | 程序化滚动期间关闭反向高亮（`lockSync`），scroll 事件 100ms 节流 |

## 2. 技术选型与框架

### 2.1 技术栈清单

| 层 | 选型 | 版本/说明 |
| --- | --- | --- |
| 客户端框架 | 微信小程序原生 | `libVersion 3.5.6`，最低支持到 2.25.0 |
| 模板/样式 | WXML / WXSS | 全程 `rpx` 布局，CSS 变量做主题令牌 |
| 逻辑 | ES6+（增强编译开启） | Promise 化异步，不使用 `async/await` 以免依赖 regenerator |
| 状态管理 | 自研 `utils/cart.js` | 发布订阅 + `wx.setStorageSync` 持久化 |
| 服务端 | Node.js（Koa/NestJS）+ MySQL + Redis | 见 [第 7 章](#7-数据与接口设计) 接口契约 |
| 支付 | 微信支付 JSAPI（小程序） | 服务端下单签名，客户端 `wx.requestPayment` |
| 消息 | 订阅消息（一次性） | 下单成功 + 出餐通知两个模板 |
| 图片/静态资源 | 无（emoji + CSS）→ 后续接 CDN + WebP | 主包体积可控 |

### 2.2 为什么是原生框架（而不是 Taro / uni-app / mpvue）

1. **只有微信一端**：本项目不做支付宝/抖音多端，跨端框架的价值直接归零，成本却全部保留（构建链、运行时适配层、H5 兼容分支）。
2. **包体与启动**：跨端框架会引入 100~200KB 运行时，本项目主包预算只有 2MB，这部分体积需要用来放业务。
3. **平台能力零延迟**：订阅消息、`chooseAvatar`、`getPhoneNumber`、`requestSubscribeMessage`、`wx.openLocation` 等能力在原生下永远是一等公民，跨端框架通常要等社区适配。
4. **排障成本**：线上问题（白屏、渲染异常）在原生下可以直接用「真机调试 + 性能面板」定位；跨端多一层转换会显著拉长出问题的定位时间。
5. **团队成本**：原生 WXML/WXSS 是每个小程序工程师的母语，无需为多端框架额外学习与维护。

### 2.3 为什么自建组件而不是引 TDesign

| 对比项 | TDesign MiniProgram | 自建（本方案） |
| --- | --- | --- |
| 引入成本 | 需 `npm install` + 「构建 npm」+ 产物提交 | 0，直接复制目录可用 |
| 体积 | 全量约 400KB+，按需仍需构建 | 2 个组件合计 < 12KB |
| 点单页交互 | Stepper 默认形态不满足「零态只显示加号 + 规格层联动 + 跳动动效」 | 完全按业务定制 |
| 品牌调性 | 通用设计语言需大量覆盖样式 | 直接按「麻辣红 + 油泼金」设计 |
| 审核风险 | 构建产物异常可能带来审核问题 | 无 |

> 结论：**只有 2 个业务组件**（`stepper`、`sku-popup`）需要自建，收益远大于成本。若后续要做会员中心/表单密集页，再按需引入 TDesign 到分包中，不影响主包。

### 2.4 状态管理选型

| 方案 | 体积 | 构建 | 本项目适配度 |
| --- | --- | --- | --- |
| MobX-miniprogram | ~40KB | 需要 | 过度设计：全局态只有「购物车」一处 |
| 自研发布订阅 store | < 2KB | 不需要 | ✅ 采用 |
| `app.globalData` 直改 | 0 | 不需要 | ❌ 无法通知多页刷新 |

自研 store 的三条设计原则（`utils/cart.js`）：

1. **单一数据源**：`cart.get()` 永远返回同一份 state；
2. **写操作即持久化 + 广播**：任何 `add / setCount / setSoup …` 都走 `persist()` → `wx.setStorageSync` → `notify()`；
3. **跨页自动同步**：点单页、购物车页、tabBar 角标各自 `subscribe`，从不手工传参。

```js
// 一处改动，三处自动刷新
cart.add(dish, { spicyId: 'sp3', spicyName: '特辣' }, 2);
//  → menu 页 countMap 更新（列表数字跳动）
//  → cart 页 items + summary 更新（金额实时变化）
//  → app.js syncCartBadge() 更新 tabBar 角标
```

#### 关键交互逻辑

**① 左右双向联动（本页技术难点）**

不采用 `IntersectionObserver`（每分类一个观察器，跨分类时回调抖动），改用「预量高度 + scroll 节流求交」：

```js
// 1) 首屏渲染完成后，一次性量出每个分类区块相对滚动内容顶部的偏移
measureSections() {
  const query = wx.createSelectorQuery();
  query.select('.dishes').boundingClientRect();        // 容器
  this.data.categories.forEach(c => query.select('#sec-' + c.id).boundingClientRect());
  query.exec(res => {
    const listRect = res[0];
    this.sectionTops = this.data.categories.map((c, i) => ({
      id: c.id,
      top: res[i + 1].top - listRect.top,               // 量高时 scrollTop = 0，可直接相减
    }));
  });
}

// 2) 右侧滚动 → 反查当前分类（100ms 节流，只在分类变化时 setData）
const handleDishScroll = throttle(function (e) {
  if (this.lockSync) return;                            // 程序化滚动期间关闭，防抖
  const tops = this.sectionTops;
  let active = tops[0].id;
  for (let i = 0; i < tops.length; i++) {
    if (e.detail.scrollTop + 6 >= tops[i].top) active = tops[i].id;
  }
  if (active !== this.data.activeCat) {
    this.setData({ activeCat: active, catScrollInto: 'cat-' + active });
  }
}, 100);

// 3) 左侧点击 → 右侧定位（480ms 锁 + 复位，保证重复点同一分类也能再次滚动）
onCatTap(e) {
  const id = e.currentTarget.dataset.id;
  this.lockSync = true;
  clearTimeout(this._lockTimer);
  this._lockTimer = setTimeout(() => {
    this.lockSync = false;
    this.setData({ dishScrollInto: '' });               // 复位，否则同值不触发 scroll-into-view
  }, 480);
  this.setData({ activeCat: id, catScrollInto: 'cat-' + id, dishScrollInto: 'sec-' + id });
}
```

> 三个坑点：**量高必须在首屏渲染后**（否则量到骨架屏）、**scroll-into-view 同值不重复触发**、**程序化滚动要关掉反向高亮**。

**② 加购的两条路径**

| 菜品类型 | 列表控件 | 交互 |
| --- | --- | --- |
| `dish.spicy === true` | 数量（只读）+ `+` | 点 `+` 弹 `sku-popup` 选辣度 → 确认加购；减数量到购物车操作 |
| `dish.spicy === false` | 完整 `stepper`（`min=0`） | 零态只显示 `+`，直连 `cart.add / cart.reduceDish` |

**为什么不给辣度菜品做列表内减号？** 因为同一菜品的不同辣度是不同明细行，列表内减号存在「减哪一条」的歧义，交给购物车处理更清晰，也减少误操作。

**③ 性能关键：不要把菜品对象塞进 dataset**

```html
<!-- ❌ 每次事件传递会序列化整个对象 -->
<view bindtap="onAdd" data-dish="{{dish}}">

<!-- ✅ 只传 id，页面内用索引表 O(1) 取 -->
<view bindtap="onAddDish" data-id="{{dish.id}}">
```
```js
// onLoad 里建索引
menu.categories.forEach(c => c.dishes.forEach(d => {
  this.dishMap[d.id] = d;
  this.dishCategory[d.id] = c.id;
}));
```

**④ 数量与角标的渲染**：`countMap`（dishId → 数量）与 `catCount`（catId → 数量）在 `cart.subscribe` 回调里一次性算好，一次 `setData`，避免每个菜品各挂一个监听。

#### 数据结构（页面 data）


### 4.4 购物车 `pages/cart/cart`

#### 整体结构（自上而下五块）

| 区块 | 内容 | 交互 |
| --- | --- | --- |
| ① 就餐信息 | 堂食/自取分段、桌号 picker、就餐人数 stepper | 切自取 → 清空桌号 + 出现 ¥1 打包费提示 |
| ② 锅底（必选 1） | 横向滚动卡片，含 emoji/名称/价格/推荐角 | 单选，切换即重算金额 |
| ③ 蘸料（可多选） | chips 组，勾选态高亮 + ✓ | 多选，免费 |
| ④ 已选明细 | 每行：emoji + 名称 + 辣度标签 + 单价 + stepper | `min=0`，减到 0 自动移除；长按二次确认删除 |

#### 关键交互逻辑

**未满足下单条件必须解释原因**（这是转化率细节）：

```js
blockReason(summary, state) {
  if (!state.items.length) return '请先选择菜品';
  if (!state.soup) return '请选择锅底';
  if (state.diningType === 'dinein' && !state.tableNo) return '请选择桌号';
  return '';
}
```

**金额计算口径（全部整数分）**：

```
goods    = Σ(item.price × item.count)
soupFee  = soup ? soup.price : 0
packFee  = (diningType === 'takeout' && count > 0) ? 100 : 0
total    = goods + soupFee + packFee
canSubmit = items.length > 0 && soup != null && (takeout || tableNo)
```

### 4.6 确认订单 `pages/confirm/confirm`

| 区块 | 说明 |
| --- | --- |
| 就餐信息复核 | 方式 / 桌号 / 人数 / 锅底 / 蘸料（只读，回购物车修改） |
| 订单明细 | 行级：名称 + 辣度 + 数量 + 金额 |

| 底部 | 实付金额 + 提交订单 |

#### 支付时序（含取消分支）

```
用户点「提交订单」
   │
   ├─▶ orderService.createOrder(payload)  →  订单落库，状态 = UNPAID
   │                                        （金额快照 / 明细快照，之后再改购物车不影响）
   ├─▶ config.MOCK_PAY = true  → wx.showModal 模拟收银台
   │   config.MOCK_PAY = false → POST /orders/:id/prepay → wx.requestPayment
   │
   ├─ 支付成功 → payOrder() → status = PAID
   │            → cart.clear(false)  ← 只清菜品，保留锅底/蘸料/就餐方式
   │            → requestSubscribeMessage([下单成功, 出餐通知])
   │            → wx.redirectTo(订单详情)
   │
   └─ 支付取消 → 订单已存在 → 弹窗「订单已生成，可在订单中继续支付（15 分钟）」
                → redirectTo(订单详情)   ← 关键：不让用户以为丢单
```

**为什么 `cart.clear(false)` 而不是全清**：保留锅底/蘸料/就餐方式，用户「再来一单」或加菜时无需重选。

**为什么订阅消息放在支付成功后**：这是用户授权意愿最高的时刻，实测接受率远高于进入首页就弹。

### 7.1 统一响应结构与错误约定


### 7.4 `utils/request.js` 设计要点

| 能力 | 实现 |
| --- | --- |
| Base URL / 版本头 | `config.BASE_URL + url`，附 `X-Client-Version`、`X-Env` |
| Token 注入 | `Authorization: Bearer <token>`，`noAuth: true` 可跳过（登录接口） |
| 业务码判定 | HTTP 2xx 且 `data.code === 0` 才 resolve，其余 reject 统一结构 |
| 401 自动重登重放 | 全局唯一 `refreshTask` 去重；`__retried` 标记保证只重放一次 |
| 并发去重 | `requestOnce()` 同 URL+同参数在飞行中不重复发起（菜单/详情页） |
| 超时 | 默认 10s，可 per-request 覆盖 |
| 错误结构 | 永远 `{ code, message, detail, requestId? }`，页面只认 `message` |

```js
// services 层：Mock / 真实后端一键切换
const task = config.USE_MOCK
  ? new Promise(resolve => setTimeout(() => resolve(localData), 180))   // 模拟 180ms 网络
  : request({ url: '/menu', method: 'GET' });
```

### 7.5 缓存策略

| 数据 | 缓存位置 | 有效期 | 失效条件 |
| --- | --- | --- | --- |
| 菜单 | `App.globalData.menuCache`（内存） | 60s | 超时 / 强制 `getMenu(true)` / 手动清缓存 |
| 购物车 | `wx.setStorageSync('lbz_cart_v1')` | 永久 | 用户清空 / 支付成功后清菜品 |
| 订单 | `wx.setStorageSync('lbz_orders_v1')` | 永久（Mock） | 真实环境由服务端持有，本地只做乐观缓存 |
| 用户 | `wx.setStorageSync('lbz_user')` | 30 天 | 过期重登 / 退出登录 |
| 取餐号序列 | `wx.setStorageSync('lbz_pickup_seq')` | 永久（Mock） | 真实环境由服务端发号 |

> Storage 单 key 上限 1MB、总上限 10MB。菜单不走 Storage（放内存），订单做**条数裁剪**（保留最近 50 条）以防长期使用溢出。

## 8. 登录与用户体系

### 8.1 三层用户模型

```
第 1 层：静默登录（openid）        —— 进入小程序即完成，用户无感
          ↓ 下单不需要任何授权，转化率最高
第 2 层：头像昵称                  —— 「我的」页用户主动填写（chooseAvatar + nickname input）
          ↓ 用于订单展示、会员称呼
第 3 层：手机号（getPhoneNumber）  —— 需企业主体 + 手机号快速验证
          ↓ 用于会员打通、储值卡、客服联系
```

### 8.2 登录时序

```
小程序启动 (app.onLaunch)
   │
   ├─ auth.ensureLogin()
   │     ├─ 本地已有 token + 用户缓存未过期 ──▶ 直接复用（0 请求）
   │     ├─ 否则 wx.login() → code
   │     │     ├─ USE_MOCK=true  → 本地伪造 openid + token（真机可完整跑通）
   │     │     └─ USE_MOCK=false → POST /auth/wechat-login { code, scene }
   │     │                         服务端 code2session → 签发自有 JWT
   │     │                         access_token（7 天）+ refresh_token（30 天）
   │     └─ 失败 → 降级为游客态，不阻塞首屏（.catch 只 warn，不 toast）
   │
   └─ 不 onLaunch 就弹任何授权框
```

### 8.3 关键实现约束

| 约束 | 说明 |
| --- | --- |
| 不用 `wx.getUserInfo` | 已废弃，只能拿到「微信用户」灰色头像 |
| 昵称/头像用新能力 | `<button open-type="chooseAvatar">` + `<input type="nickname">` |
| 头像临时文件 | `chooseAvatar` 返回临时路径，先 `copyFileSync` 到 `wx.env.USER_DATA_PATH`，再上传 |
| 登录态校验 | 关键操作前 `wx.checkSession`，失败则静默重登 |
| 401 收敛 | 只在 `request.js` 一处处理，页面无感 |
| 退出登录 | `auth.logout()` 清 token + 用户缓存（「我的 → 清除本地缓存」可一键重置） |

### 8.4 隐私合规（必做，否则无法过审）

1. 在小程序后台配置 **「用户隐私保护指引」**，逐项声明：昵称、头像、手机号、位置信息、相册；
2. `app.json` 中声明 `permission.scope.userLocation` 及其用途描述（本项目用于就近门店与配送范围）；
3. 未声明 `requiredPrivateInfos`（本项目不采集 `getLocation` 之外的敏感隐私）；
4. 首次触发隐私接口前会由微信自动弹出隐私协议，**不要自建二次弹窗**；
5. 用户拒绝授权时，所有功能须能降级（本项目：拒绝位置 → 门店地址改为静态展示；拒绝头像昵称 → 显示「微信用户」+ emoji 占位）。

## 9. 性能优化与分包加载策略

### 9.1 体积预算与分包方案

| 包 | 内容 | 预算 | 实测（本工程） |
| --- | --- | --- | --- |
| 主包 | app + utils + services + mock + components + 4 个 tab 页 + confirm + order-detail | **≤ 1.5MB**（硬上限 2MB） | ~180KB（无图片资源） |
| 分包 `packageUser` | 优惠券、后续会员中心/储值卡/地址簿 | ≤ 800KB | ~8KB |
| 总包 | — | ≤ 20MB | — |

```jsonc
// app.json
{
  "subPackages": [
    { "root": "packageUser", "name": "user", "pages": ["pages/coupon/coupon"] }
  ],
  "preloadRule": {                            // 分包预下载：用户几乎一定会点「我的」
    "pages/mine/mine":  { "network": "all", "packages": ["user"] },
    "pages/confirm/confirm": { "network": "all", "packages": ["user"] }
  },
  "lazyCodeLoading": "requiredComponents"     // 按需注入，减少启动时 JS 执行量
}
```

**分包划分原则**：主包只放「下单主链路」，一切**非下单必经**的页面（券、会员、地址、储值、活动）全部下沉分包。

### 9.2 启动性能

| 手段 | 效果 |
| --- | --- |
| `lazyCodeLoading: "requiredComponents"` | 只注入当前页面用到的组件 JS，冷启动 JS 执行量下降 |
| 首屏零图片 | 无图片解码，无 404 风险，首屏只跑 1 次逻辑请求 |
| 骨架屏 | Mock 180ms / 真实 ≤500ms 内展示骨架，感知等待大幅降低 |
| 首屏数据不阻塞渲染 | `setData(loading:false)` 后再 `wx.nextTick` 量高 |
| 静默登录不阻塞 | `onLaunch` 里 Promise 异步，失败只 warn |
| 预加载分包 | 进入「我的」或「结算」时静默下载 `packageUser` |

**目标**：中端 Android 冷启动到「可点串」≤ 1.5s。

### 9.3 渲染性能（setData 是最贵的操作）

| 反模式 | 本方案做法 |
| --- | --- |
| 每个菜品挂一个监听 | 一个 `cart.subscribe` 回调里算好 `countMap + catCount`，**一次 setData** |
| `data-dish="{{dish}}"` 传递对象 | 只传 `data-id="{{dish.id}}"`，页面内 `dishMap` 索引取对象 |
| scroll 事件里直接 setData | `throttle(100ms)` + 仅在 `activeCat` 真正变化时 setData |
| 每次输入都写 Storage | 备注本地 state 暂存，`bindblur` / 提交时才落库 |
| 轮询高频刷新整页 | 5s 轮询且仅 `setData({order})`；已结束订单立即停止轮询 |

### 9.4 长列表与滚动

| 场景 | 方案 |
| --- | --- |
| 菜品列表（30~200 项） | 左分类 + 右 `scroll-view` 锚点分区；分类多时左栏本身也是 `scroll-view` |
| 订单列表 | 分页（`page/size`）+ 上拉加载；列表项已剔除详情字段 |
| 分类联动 | 见 4.3，预量高度 + 节流求交，避免 N 个 `IntersectionObserver` |

### 9.5 图片与资源

| 阶段 | 方案 |
| --- | --- |
| MVP（当前） | emoji + CSS 渐变底，**零图片资源**，包体最小、真机永不塌陷 |
| 接真实菜品图 | CDN + WebP 优先（微信 WebView 支持），`<image mode="aspectFill" lazy-load>`，宽高比固定 1:1 防抖 |
| 图标 | tabBar 需要时用 `iconPath` 小 PNG，或改用自定义 tabBar（`custom-tab-bar`）获得完全控制 |

### 9.6 稳定性与监控

| 手段 | 实现 |
| --- | --- |
| 全局异常 | `app.js` 里 `wx.onError` 采样上报 |
| 启动耗时 | `onLaunch` 记 `launchTs`，首屏渲染完成后上报差值 |
| 关键路径埋点 | 见 12.4 事件表 |
| 降级 | 菜单加载失败 → 保留骨架 + toast 重试；购物车/订单存储在本地，接口挂掉仍可看单 |
| 真机崩溃 | 关注「小程序后台 → 运维中心」错误率（目标 < 0.1%），并订阅告警 |

| **微信搜一搜** | 小程序名含「串串香/簋街」等词，配合 `sitemap.json` 允许索引点单页与订单页 | `sitemap.json` 已 allow 点单页/订单页，disallow 结算与详情页 |
| **社交分享** | 点单页与「我的」页均已实现 `onShareAppMessage`；「我的」页额外实现 `onShareTimeline`（朋友圈） | 已实现，文案走「品牌 + 卖点」而非诱导 |
| **公众号绑定 + 视频号挂载** | 公众号菜单挂小程序、视频号主页挂小程序 | 需后台绑定（同一主体） |

**裂变设计（合规做法）**：新客券 `cp1` 由系统在新用户首访时**自动发放到账户**，无需分享；老带新的激励放在「被邀请人下单后给邀请人发券」，不发「分享即得」，规避诱导分享驳回。

### 12.3 转化率优化点（点单页已内建）

| 细节 | 作用 |
| --- | --- |
| 锅底默认预选 | 减少 1 次必选操作，避免卡在结算 |
| 辣度默认「微微辣」 | 降低决策成本，降低「太辣」差评 |
| 无规格菜品一键加购 + 轻震动 | 提升加购爽感，加快「30 秒选 10 串」节奏 |
| 悬浮购物车条常驻显示金额与件数 | 消除「我选了多少/多少钱」的不确定感 |
| 骨架屏 | 弱网下不出现空白页 |
| 支付取消后订单保留可继续支付 | 避免用户误以为丢单而放弃 |
| 未满足条件时提示「差什么」 | 替代灰按钮无解释，减少放弃率 |

### 12.4 指标体系与埋点

| 阶段 | 指标 | 目标 | 埋点事件 |
| --- | --- | --- | --- |
| 获客 | 扫码进入 UV、分享带来的新用户占比 | 分享新客 ≥ 15% | `scan_enter{source, tableNo}`、`share_click{scene}` |
| 激活 | 点单页 → 加入购物车率 | ≥ 60% | `dish_add{dishId, spicyId, count, from:'list'|'sku'}` |
| 转化 | 加购 → 提交订单率；提交 → 支付成功率 | ≥ 45% / ≥ 92% | `order_submit{amount, itemCount}`、`order_pay_result{result}` |
| 效率 | 首单耗时（进入 → 支付成功） | ≤ 120s | `time_to_first_order` |
| 履约 | 出餐时长、状态轮询到 READY 的间隔 | ≤ 8 分钟 | `order_ready{orderId, duration}` |
| 留存 | 7 日回访率、复购率（30 天 2 单以上） | ≥ 25% / ≥ 20% | `user_return{days}`、`order_repeat` |
| 稳定性 | 错误率、启动耗时 P90 | < 0.1% / ≤ 1.5s | `wx.onError` 采样、`launch_cost` |
| 体验 | 分享打开率、订阅消息点击率 | ≥ 15% / ≥ 8% | `share_open`、`subscribe_click` |

> 埋点统一走 `utils/analytics.js`（可对接微信自定义分析或自建上报），**采样 + 批量上报**，禁止逐事件同步请求。
