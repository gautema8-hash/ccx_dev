## 2. 高并发实测数据（这是「能不能扛住」的硬证据）

### 2.1 防超卖：60 并发抢 20 件库存

| 指标 | 结果 |
| --- | --- |
| 成功下单 | **20 笔**（正好等于库存） |
| 库存不足被拒 | **40 笔**（返回 42001，提示「库存不足，请调整数量」） |
| 其他类型失败 | **0** |
| 数据库剩余库存 | **0**（精确归零，无超卖、无少卖） |
| 销量字段 | 准确累加 |

**实现方式**：`UPDATE mp_dish SET stock = stock - ? WHERE id = ? AND status = 1 AND stock >= ?`，
靠 `affectedRows === 0` 判定失败。不是「先查再减」，所以**不存在检查与扣减之间的竞态窗口**。
并且扣减前按 `dishId` 排序，让并发事务以相同顺序加锁，规避死锁。

## 3. 测试过程中发现并修复的缺陷（共 11 项）

> 下面每一条都是**真实跑出来的**，不是纸面推演。其中 4 条只有并发/真实后端场景才会暴露。

### 🔴 P1 · 已支付订单能被直接取消 → 钱不退（资金安全）

**发现方式**：接口测试第 12 节。
**问题**：`cancelOrder` 允许 `UNPAID` 和 `PAID` 两种状态取消，但只对 `UNPAID` 做库存回滚和券退回。
已支付订单被取消后，订单变 `CANCELED`，**用户的钱没有任何退款动作**。
**修复**：取消只允许未支付；已支付必须走 `applyRefund`（门店审核后原路退回）。
客户端的 `canCancel` 同步改为仅未支付，已支付显示「申请退款」。

### 🔴 P1 · 优惠券核销 SQL 列名被覆盖（券根本核销不了）

**发现方式**：并发测试第 5 节（4 次并发使用同一张券，0 次成功）。
**问题**：

```sql
SELECT uc.id, c.* FROM mp_user_coupon uc JOIN mp_coupon c ...
```

`c.*` 里也带 `id`，**把 `uc.id` 覆盖了**。后续 `WHERE id = ?` 传进去的是券模板 id（`cp1`），
MySQL 报 `Truncated incorrect INTEGER value: 'cp1'` → 500。
**影响**：优惠券功能完全不可用（一用就报错）。
**修复**：显式起别名 `SELECT uc.id AS uc_row_id, c.id AS coupon_id, ...`。

### 🔴 P1 · 订单号并发撞号（同一秒下单必挂）

**发现方式**：并发测试第 7 节混合负载出现 10 个 5xx。
**问题**：订单号 = `LBZ + 秒级时间戳 + 3 位随机`，同一秒内并发下单时 3 位随机只有 1000 种取值，
生日悖论下必然碰撞，撞上 `uk_order_no` 唯一键 → 500。
**修复**：改为 `LBZ + yyyyMMdd + 8 位全局递增序列`（序列来自 `mp_seq`，配日期天然唯一且可读）。

### 🔴 P1 · 取号序列在并发下会取重（连接池 + LAST_INSERT_ID 的坑）

**发现方式**：修复上一项时顺带定位到根因。
**问题**：`UPDATE mp_seq SET val = LAST_INSERT_ID(val+1)` 依赖 `LAST_INSERT_ID()` 与 `UPDATE`
在**同一连接**上；连接池里下一次查询大概率换连接 → 读到 0 或别的值。
即便改成「先 UPDATE 再 SELECT」，两个并发事务也会读到同一个 val。
**修复**：改为事务内 `SELECT ... FOR UPDATE` + `UPDATE`，把同一序列名的取号串行化。

### 🟠 P2 · 下单频次限流把「校验失败」也算进配额

**问题**：限流在参数校验之后就计数，但库存不足、菜品不存在等业务失败也会消耗配额。
用户填错两次表单就被锁 15 分钟 —— 对餐饮场景是不可接受的体验。
**修复**：拆成 `peek`（只读判断）+ `incr`（成功后才计数），语义变成「只统计成功下单」。

### 🟠 P2 · 登录限流按 IP 限 30/分钟 → 餐厅 WiFi 全店被锁

**发现方式**：并发测试需要 60 个用户同时登录，一半被 429。
**问题**：餐厅 WiFi 是 NAT 出口，**全场顾客共用一个公网 IP**。30 次/分钟的阈值意味着
高峰时段第 31 位顾客之后全部登录失败。
**修复**：阈值放宽到 300/分钟；真正的防刷靠「code 一次性 + 短时效」，不靠 IP 严限。

### 🟠 P2 · 下单请求传 `items:[null]` 直接 500

**发现方式**：健壮性测试 A 节。
**问题**：`String(it.dishId || '')` 在 `it` 为 `null` 时抛 `Cannot read properties of null`。
**修复**：遍历前先校验「必须是对象」。

### 🟠 P2 · `page=1e308` 没有上界 → OFFSET 溢出

**问题**：只做了 `Math.max(1, page)` 下限，`Number('1e308')` 是有限数，直接变成 `OFFSET 1e308`。
**修复**：上下界都要卡（page ≤ 10000，size ≤ 20）。

### 🟠 P2 · 超大 body 直接 `destroy()` 连接 → 客户端只看到「网络异常」

**问题**：`req.destroy()` 会在客户端还在写的时候就掐断连接，客户端拿到的是 socket 错误，
而不是「请求体过大」。用户会以为是网络问题反复重试。
**修复**：判超限后**只停止累积**（防内存膨胀），不掐连接，让 413 正常写回。

### 🟡 P3 · 真实后端模式下订单详情页状态不刷新

**问题**：详情页轮询调用的是 `orderService.refreshStatus()`，而该函数在非 mock 模式下返回 `null`
—— 用户停在详情页永远看不到「商家已接单 / 已出餐」，必须退出重进。
**修复**：轮询在真实模式下改为重新请求 `GET /orders/:id`（失败静默重试，不打断用户）。

### 🟡 P3 · `db reset` 不清理 Redis → 自增 ID 复用后限流计数错位

**问题**：`reset` 只重建了表，Redis 里的限流/锁/缓存键还留着。表重建后自增 ID 从 1 开始，
新用户会撞上旧用户的限流计数，导致「刚下载的数据库就提示下单过于频繁」。
**修复**：`reset` 同时 flush 应用命名空间下的所有 Redis 键。
（踩坑点：带 `keyPrefix` 的客户端做 SCAN + DEL 会二次加前缀，一个键都删不掉 —— 必须用独立的不带前缀的连接。）

## 4. 安全性审查结论

| 风险项 | 检查方式 | 结论 |
| --- | --- | --- |
| **金额篡改** | 客户端伪造 `amount.pay=1` 下单 | ✅ 服务端完全丢弃客户端金额，按 DB 价格重算 |
| **支付金额不符** | 伪造回调金额 | ✅ `settlePaid` 比对 `pay_amount`，不符直接拒绝并记 error 日志 |
| **JWT 伪造** | 篡改 payload 的 `uid` | ✅ `timingSafeEqual` 校验签名，返回 401 |
| **alg=none 攻击** | 伪造无签名 token | ✅ 拒绝（签名算法写死 HS256） |
| **越权访问** | 用 B 的 token 读/取消 A 的订单 | ✅ 所有按 id 的查询都带 `user_id` 条件，返回 404 |
| **SQL 注入** | 4 种注入串打所有接口 | ✅ 全部参数化查询，无 5xx，订单表完好 |
| **XSS** | 昵称写 `<script>alert(1)</script>` | ✅ 原样存储、客户端转义渲染；头像拒 `javascript:` / `data:` |
| **路径穿越** | `/uploads/../package.json` 等 3 种 | ✅ 全部 400/404，且 `path.resolve` 校验前缀 |
| **后台越权** | 无/错 `X-Admin-Token` | ✅ 定时安全比较，返回 403 |
| **重放攻击** | 回调时间戳偏移 > 5 分钟 | ✅ 拒绝 |
| **回调伪造** | 未验签的 notify | ✅ 先验签再解密；mock 模式下也走同一套幂等与金额校验 |
| **券重复使用** | 并发 4 次用同一张券 | ✅ 条件更新 `WHERE status='UNUSED'`，只成功 1 次 |
| **隐私** | 手机号解密 | ✅ 校验 watermark.appid 与本站一致 |
| **敏感日志** | token/手机号/openid 落日志 | ✅ 日志层统一脱敏 |

## 5. 稳定性与容错审查结论

| 场景 | 结论 |
| --- | --- |
| **Redis 完全不可用** | ✅ 服务照常启动并标明 `degraded`；菜单穿透到 DB、登录/下单/支付全部可用、限流与锁降级为进程内实现；**幂等依然生效**（DB 唯一键兜底） |
| 坏 JSON / 空 body | ✅ 400 + 可读提示，不崩 |
| 超大 body | ✅ 413，且不掐连接、不膨胀内存 |
| 类型错乱 / null 元素 / emoji / 控制字符 | ✅ 业务错误或不崩，无 5xx |
| 未知路由 / 错误方法 | ✅ 404 / 405 |
| 优雅退出 | ✅ 摘流量后新请求被拒，在途请求跑完，端口正常释放 |
| 进程级异常 | ✅ `uncaughtException` / `unhandledRejection` 全部落结构化日志，前者触发优雅退出（进程状态已不可信时不硬撑） |
| 连接池 | ✅ 事务内不再额外取连接（取号移到事务外），避免池耗尽 |
| 慢请求 | ✅ 超过 1s 自动记 warn 日志；单请求 15s 超时兜底 |

| 项 | 数据 / 措施 |

| 混合负载延迟 | P50 **38ms** / P95 **143ms** / P99 156ms（120 并发请求） |
