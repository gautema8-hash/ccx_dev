## 2. 技术栈

### 2.1 选型与理由

| 层 | 技术 | 理由 |
| --- | --- | --- |
| 小程序 | **微信原生框架** | 单端投放、包体最小、平台新能力零适配；不引 Taro/uni-app |
| 小程序 UI | **无组件库**（自建 `stepper` / `sku-popup`） | 连锁主题换肤需要完全掌控 CSS 变量，第三方组件库会成为阻碍 |
| 小程序状态 | **自研发布订阅 store**（`utils/cart.js`） | 只用一个购物车状态中心，引 MobX 属过度设计 |
| 后端运行时 | **Node.js ≥ 18** | 与小程序同语言，前后端可复用校验逻辑 |
| 后端 Web 框架 | **无**（自研 `http.js`，357 行） | 供应链面最小；过载保护/优雅关闭/错误码语义完全可控；实测 P95 168 ms |
| 后端依赖 | **仅 `mysql2` + `ioredis`** | 两个包可人工审计 |
| 数据库 | **MySQL 8** | 事务、行锁、唯一键是防超卖与防重复核销的基石 |
| 缓存/锁 | **Redis 5+** | 限流、分布式锁、幂等、菜单缓存；**可整体降级** |
| 管理后台 | **原生 JS 单文件**（无构建） | 内网工具，无需打包链路；CSP 收敛资源来源 |
| 小程序图片 | **emoji + CSS 渐变占位** | 零图片资源，真机样式永不塌陷 |

### 2.2 版本与依赖

| 项 | 版本/取值 |
| --- | --- |
| Node.js | ≥ 18（实测 22.22.2） |
| MySQL | 8.x（实测 8.0.44） |
| Redis | 5.x+（实测 5.0.14.1） |
| 后端直接依赖 | `mysql2 ^3.11.3`、`ioredis ^5.4.1` |
| 小程序 | 原生，`lazyCodeLoading: requiredComponents` |

### 3.3 分层依赖规则（强制）

```
页面/组件  →  services  →  utils/request  →  后端 API
                ↓
              mock（仅 USE_MOCK 时）
```

| 禁止 | 原因 |
| --- | --- |
| 页面直接 `wx.request` | 绕过统一鉴权、重试、错误处理 |
| 页面直接读 `mock/` | 真实后端与 mock 切换会失控 |
| WXML 里计算价格 | 价格必须服务端给或服务端口径 |
| 业务代码自行拼 `store_id` 条件 | 漏一处就是数据泄露 |

## 4. 数据架构

### 4.1 分域表清单（27 张）

| 域 | 表 |
| --- | --- |
| 品牌门店 | `mp_brand` `mp_store` |
| 账号权限 | `mp_staff` `mp_staff_store` `mp_audit_log` `mp_login_log` |
| 菜单库存 | `mp_category` `mp_dish` `mp_soup` `mp_dip` `mp_spicy` `mp_store_dish` |
| 订单支付 | `mp_order` `mp_order_item` `mp_order_log` `mp_pay_record` `mp_refund` `mp_feedback` `mp_idempotency` `mp_seq` |
| 用户 | `mp_user` `mp_invoice` |
| 优惠券 | `mp_coupon` `mp_user_coupon` `mp_coupon_receive` |
| 团购券 | `mp_voucher` |
| 主题 | `mp_theme` |

### 4.2 核心实体关系

```
Brand 1─N Store ── type: DIRECT|FRANCHISE
                 ── franchisee / region / lat,lng / open_time
   │
   ├─1─N Dish（总部：卖什么、指导价）
   │        └──N StoreDish（门店：库存 / 改价 / 停售）
   ├─1─N Coupon（可限定 store_ids）
   ├─1─N Theme（store_id 空 = 品牌级；非空 = 门店级）
   └─1─N Staff ──N StaffStore（门店授权）

Store 1─N Order ──N OrderItem
User  1─N Order
User  1─N UserCoupon  N─1 Coupon
Platform+Code 1─1 Voucher（唯一键防重）
```

### 4.3 关键设计

| 设计 | 说明 |
| --- | --- |
| **总部定价 / 门店管货** | `mp_dish` 属品牌；`mp_store_dish` 覆盖库存与价格。菜单用 `COALESCE(NULLIF(price_override,0), price)` 一次取全 |
| **订单冗余门店维度** | `mp_order` 存 `brand_id` / `store_id` / `store_type`，隔离与统计无需 join |
| **金额一律「分」** | 整数运算，杜绝浮点误差 |
| **唯一键兜底并发** | `mp_voucher` 的 `uk(platform, code)` 是防重复核销的物理保证 |
| **序号独立循环** | 取餐号按 `pickup:{storeId}:{date}`，避免多店串号 |

## 5. 数据流

### 5.1 下单数据流（写路径）

```
小程序                          服务端                        数据层
  │ POST /orders (Idempotency-Key)
  ├─ 购物车快照 ─────────▶ 参数校验（项/数量/类型）
  │                        ├─ 解析门店（默认取直营+编码最小）
  │                        ├─ 开启事务
  │                        ├─ 读菜品（门店价 + 门店在售状态）
  │                        ├─ 原子扣库存 ─────────────▶ UPDATE mp_store_dish
  │                        │                            WHERE stock >= ?
  │                        ├─ 服务端计价（客户端传价丢弃）
  │                        ├─ 券抵扣（couponService.calcDiscount）
  │                        ├─ 生成单号（nextSeq 事务行锁）──▶ mp_seq
  │                        └─ 落库订单 + 明细 + 日志 ──────▶ mp_order*
  │◀── 返回订单 ───────────┘
  │ POST /orders/:id/prepay ──▶ 微信统一下单（或 mock）
  │ wx.requestPayment
  │ 微信回调 /pay/notify ───▶ 验签 + 解密 + 金额比对 + 幂等 ─▶ PAID
```

### 5.2 菜单数据流（读路径，热点）

```
小程序 GET /menu?storeId=
  → Redis 缓存命中（key: menu:{storeId}，60s）？ 直接返回
  → 未命中：查 mp_category + mp_dish LEFT JOIN mp_store_dish + mp_soup/mp_dip/mp_spicy
  → 组装（过滤门店停售）→ 写缓存 → 返回
```

- 带坐标请求**不缓存**（距离随位置变）。
- 运营改价/改库存/上下架 → 主动 `refreshMenuCache(storeId)` 失效。
- 小程序侧另有 60 s 内存缓存，且**按门店隔离**（换店必重新拉）。

### 5.3 主题数据流

```
运营端配置 mp_theme（品牌级/门店级 + 时间窗 + priority）
  → 小程序 GET /theme?storeId=
  → themeService.resolveTheme()：
      WHERE brand_id AND status=1
        AND (store_id = ? OR store_id='')
        AND 时间窗内
      ORDER BY (store_id = ?) DESC, priority DESC
  → mergeTokens（差异合并到默认令牌 + 白名单过滤）
  → 返回 tokens + style（CSS 变量串）
  → 页面根节点 style="{{themeStyle}}"，CSS 变量向下继承
```

### 5.4 核销数据流

```
券码 → normalizeCode（去空格/连字符、大写）
  → 本地查重 mp_voucher（platform, code）
  → provider.verify()（mock 规则 / 美团开放平台）
  → 面值上限保护
  → INSERT（唯一键兜底）
  → 写审计 mp_audit_log
```

## 6. 部署拓扑

系统**同时支持单节点与多节点（集群）**两种部署模式。两种模式使用同一份代码与配置，差别仅在进程编排与外部组件。

### 6.1 模式 A：单节点（起步 / 小规模）

```
用户 ──HTTPS──▶ [Nginx:443] ──proxy──▶ [Node:3000]
                                          ├─▶ MySQL（同机或独立）
                                          └─▶ Redis（同机或独立）
管理后台 ──────▶ [Nginx:443/admin]
```

- 适用：单店、试点、日订单量较低阶段（`TODO`：明确切换阈值）。
- 特点：部署简单，无共享状态问题；单机故障即整体不可用。
- 上传目录 `uploads/` 在本机磁盘即可。
- 配置：`deploy/nginx-single.conf`、`deploy/lbz-order.service`。

### 6.2 模式 B：多节点集群（面向全国用户）

```
                    ┌──────────── 用户（全国）────────────┐
                    │  微信小程序 / 管理后台               │
                    └───────────────┬────────────────────┘
                                    │ DNS
                          ┌─────────▼─────────┐
                          │  负载均衡（Nginx / CLB）│
                          │  TLS 终止 + 健康检查    │
                          └────┬────┬────┬────────┘
                               │    │    │  （轮询 / least_conn）
                    ┌──────────┘    │    └──────────┐
              ┌─────▼─────┐  ┌─────▼─────┐  ┌──────▼────┐
              │ Node 实例 1│  │ Node 实例 2│  │ Node 实例 N│   ← 无状态，可水平扩展
              └─────┬─────┘  └─────┬─────┘  └──────┬────┘
                    └──────────┬───┴───────────────┘
                               │
              ┌────────────────┼─────────────────┐
        ┌─────▼─────┐   ┌──────▼──────┐   ┌──────▼──────┐
        │ Redis     │   │ MySQL 主    │   │ 对象存储     │
        │（共享）    │   │  ├─ 从库(读) │   │（上传文件）  │
        └───────────┘   └─────────────┘   └─────────────┘
```

**水平扩展**：应用无状态，新增实例只需启进程并注册到 upstream。扩缩容不影响在线请求（配合优雅关闭）。

**会话共享**：不使用服务端 Session。
- 用户端：JWT（HMAC 签名），任意实例可独立校验，**无需共享会话**。
- 员工端：JWT + jti 黑名单（存 Redis），**黑名单是共享的**。
- 结论：只要 Redis 共享，会话即共享。

**缓存共享**：菜单缓存、限流计数、幂等键、分布式锁、支付回调去重全部走 Redis → 天然共享。

**数据一致性**：
| 场景 | 保证 |
| --- | --- |
| 库存扣减 | `UPDATE ... WHERE stock >= ?` 原子语句 + 事务，跨实例同样安全 |
| 订单号 / 取餐号 | `mp_seq` 事务内 `SELECT ... FOR UPDATE` 行锁，跨实例不重复 |
| 幂等 | Redis 幂等键（共享）；Redis 不可用时退化为 DB 唯一键 |
| 券防重复核销 | DB 唯一键 `uk(platform, code)`，**不依赖缓存** |
| 券防超发 | `UPDATE ... WHERE issued < total` 条件更新 |
| 缓存与 DB 不一致 | 写操作主动失效缓存；缓存 TTL 60 s 兜底 |

**高可用**：
- 应用多实例 + LB 健康检查（`/ready`），单实例故障自动摘除。
- Redis：建议主从 + 哨兵（或托管实例）；故障时应用自动降级为进程内实现，服务不中断（限流与锁退化为单机语义，见风险 R-03）。
- MySQL：建议主从；故障时 `/ready` 返回 503，LB 摘除节点。
- 优雅关闭：发布时先摘流量 → 等在途完成 → 下线，滚动发布无中断。

**多节点的前置条件（重要）**：
| 项 | 原因 |
| --- | --- |
| 上传目录必须改对象存储 | 本地 `uploads/` 只在写入实例上可见，其他实例读不到，会出现头像 404 |
| Redis 必须共享且持久化 | 限流/锁/幂等退化会导致计数不一致 |
| 反向代理必须带 `X-Forwarded-For` | 限流按真实 IP 计，否则全国用户被算成同一个 IP |

### 6.3 两种模式对比

| 维度 | 单节点 | 多节点集群 |
| --- | --- | --- |
| 部署复杂度 | 低 | 中（需 LB、共享 Redis、对象存储） |
| 可用性 | 单机故障即中断 | 单实例故障无感 |
| 扩展方式 | 垂直扩容 | 水平加实例 |
| 上传文件 | 本地磁盘 | **必须对象存储** |
| 限流/锁 | 进程内或 Redis | **必须 Redis** |
| 适用阶段 | 试点、单店 | 全国连锁（`TODO`：给出切换阈值） |

## 7. 关键架构决策记录（ADR）

| # | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-01 | 不用 Web 框架，自研 `http.js` | Express / Fastify / Nest | 供应链面最小；过载保护、优雅关闭、错误码语义完全可控；实测性能达标 |
| ADR-02 | 数据隔离在 SQL 层 | 查出后再过滤 | 漏判时的后果是「查不到」而不是「泄露」 |
| ADR-03 | 门店范围校验独立于权限点 | 只校验权限点 | 区域经理有 `theme:write` 但范围受限，只校验权限点会产生越权 |
| ADR-04 | 主题令牌差异式合并 | 整套替换 | 新增主题不必抄全部令牌；改默认色只改一处 |
| ADR-05 | 团购券 Provider 可插拔 | 直接写死美团调用 | 无凭据也能全链路跑通；上线只改配置不改代码 |
| ADR-06 | 抵扣口径收口在 `calcDiscount()` | 各处自行计算 | 避免「列表显示可用、下单说不可用」「页面显示 ¥10、实付 ¥8」 |
| ADR-07 | 券撤销不释放券码 | 撤销后可再核销 | 防止「撤销 → 再核销」套现 |
| ADR-08 | 打包费等金额由服务端下发 | 客户端写死 | 运营改配置后不会出现展示与实付不一致 |
| ADR-09 | 管理后台单文件、无构建 | React/Vue + 打包 | 内网工具，无构建链路；CSP 收敛资源来源 |
| ADR-10 | 用户端与员工端两套令牌体系 | 共用一套 | 密钥域、时效、吊销策略不同；避免小程序令牌能登录后台 |
